4.4微服务架构

4.4 微服务的体系结构 · 详细讲解

云计算 / 云原生架构（重点 · 掌握）｜ 微服务概念与特性、分布式数据管理、灵活性与可扩展性

考纲要求：掌握

1微服务及其特性与架构

定义：微服务架构（Microservices Architecture）是一种将单一应用程序拆分为一组小型、松耦合、围绕业务领域组织、可独立开发部署的服务的架构风格。 每个服务运行在独立的进程中，服务间通过轻量级通信机制（如 HTTP/REST、消息队列）交互，并拥有自己的数据存储。

1.1 微服务 vs 单体架构（必考对比）

对比维度单体架构（Monolith）微服务架构（Microservices）
部署单位整个应用打包为一个部署包每个服务独立打包、独立部署
耦合度模块间紧耦合，改一处需整体重测服务间松耦合，边界清晰
数据通常共享一个数据库每个服务拥有独立数据库（去中心化）
技术栈全系统统一一种语言/框架技术异构，各服务按需选型
扩展只能整体水平/垂直扩展仅对热点服务独立扩缩容
故障影响一处崩溃 → 整个应用不可用故障隔离，单服务故障可降级
团队大团队协同同一代码库小团队端到端自治（康威定律）
图 1：单体架构（紧耦合、共享库）与微服务架构（松耦合、独立库）对比

1.2 微服务的核心特性（掌握，选择题/判断题常考）

单一职责

一个服务只做一件事，围绕业务领域（DDD）划分边界。

独立部署

每个服务可单独编译、测试、发布，不牵动整体。

松耦合

服务间通过定义良好的接口/契约通信，内部实现可改。

去中心化

数据去中心化（各管各库）+ 治理去中心化（非统一中央管控）。

技术异构

不同服务可用不同语言/框架/存储，因材施用。

故障隔离

单服务崩溃被隔离，配合熔断降级，不影响全局。

轻量通信

HTTP/REST、gRPC、消息队列等轻量级协议，非重量级 ESB。

可独立扩缩

只对负载高的服务扩容，资源利用率高。

1.3 典型微服务架构组成（支撑组件）

微服务 ≠ 只是把代码拆开。要落地微服务，必须配套一整套"基础设施（微服务全家桶）"来解决"服务在哪、怎么调用、如何容错、如何观测"的问题。
组件作用代表技术
服务注册与发现服务启动时登记地址，调用方动态查询，应对实例扩缩Nacos、Eureka、Consul、ZooKeeper
API 网关统一入口：路由、认证、限流、日志，屏蔽内部细节Spring Cloud Gateway、Kong、Nginx
配置中心配置集中管理、动态下发，无需重启服务Nacos、Apollo、Spring Cloud Config
服务通信同步（REST/gRPC）或异步（消息），定义调用方式Feign、gRPC、Dubbo、OpenFeign
容错治理熔断、降级、限流、重试，防止故障雪崩Sentinel、Hystrix、Resilience4j
链路追踪跨服务调用链监控，定位慢/错节点SkyWalking、Zipkin、Jaeger
容器与编排服务打包、调度、弹性伸缩，微服务最佳载体Docker + Kubernetes
事件/消息异步解耦、事件驱动、保证最终一致Kafka、RocketMQ、RabbitMQ
图 2：微服务体系结构全景——网关入口 + 注册/配置中心 + 独立服务与数据库 + 消息/追踪支撑
考试重点：① 微服务核心特征是单一职责、独立部署、松耦合、去中心化（数据+治理）、技术异构、故障隔离； ② 微服务"全家桶"常考组件：注册中心、API 网关、配置中心、熔断限流、链路追踪、容器编排； ③ 与 2.2 联系：分布式服务框架（Dubbo/Spring Cloud）正是支撑微服务的工具。

2微服务架构下的分布式数据管理

核心原则：Database per Service（每个服务拥有自己的数据库）。微服务强调数据去中心化—— 每个服务独占自己的数据存储，不允许其他服务直接访问其数据库，只能通过该服务暴露的接口读写数据。 这保证了服务边界的纯粹性，却也带来了分布式数据一致性这一最大难题。

2.1 为什么数据管理变难了

本质矛盾：
  • 业务操作常需跨多个服务（如"下单"要同时扣库存、扣余额、建订单）。
  • 各服务数据分布在不同库、甚至可能不同数据库类型。
  • 无法用单机数据库的事务（ACID）保证跨库原子性。
约束来源：
  • 回到 2.2 的 CAP 定理：分布式下分区 P 不可避免。
  • 强一致(C)与高可用(A)需取舍，微服务多走 AP + 最终一致。
  • 因此出现 BASE 思想（基本可用、软状态、最终一致）。

2.2 分布式事务与一致性解决方案（重点）

方案思路特点 / 适用
Saga 模式 把一个跨服务"大事务"拆成一系列本地事务；任一步失败，则按相反顺序执行补偿（Compensation）操作回滚 无锁、长事务友好；分编排(Choreography, 事件驱动)与协同(Orchestration, 中央协调器)两种
TCC 模式 Try（预留资源）→ Confirm（确认）/ Cancel（取消），两阶段业务补偿 强一致、性能好但侵入业务代码，需手写三个接口
事件溯源
Event Sourcing		 不存"当前状态"，而存状态变化的事件序列；当前状态由重放事件得到 审计友好、可追溯；实现复杂，需配合快照
CQRS 读写分离：写模型（命令侧）与读模型（查询侧）用不同模型/存储 读多写少、查询复杂场景性能高；架构变复杂
可靠事件 / 消息队列 通过消息中间件异步通知，配合"本地消息表/事务消息"保证事件不丢 实现最终一致性的工程常用手段（Kafka/RocketMQ 事务消息）
图 3：Saga（编排式）跨服务流程——本地事务 + 消息驱动 + 失败补偿回滚
一句话记忆："每个服务各管各的库"是微服务的基石，代价是跨服务数据一致性。 工程上常用 最终一致性 取代强一致：要么走 Saga（补偿回滚）、TCC（预留+确认/取消）， 要么用 消息队列 + 事务消息 保证事件可靠、异步达成最终一致；需要审计/复杂查询时上 事件溯源 / CQRS。
考试重点：① Database per Service 是数据管理第一原则；② 跨服务事务靠 Saga / TCC / 消息最终一致；③ 微服务数据一致性多遵循 BASE（最终一致），与 2.2 的 CAP/AP 一脉相承； ④ "直接让服务 A 读写服务 B 的数据库"是反模式（破坏边界、耦合）。

3微服务如何提升灵活性与可扩展性

本质：微服务把"一个大铁板"切成"一群可独立运动的小积木"。正因为每个积木独立部署、独立扩缩、技术自决， 系统整体就获得了单体架构难以企及的灵活性（改得动、换得掉）与可扩展性（撑得住、花得省）。

3.1 灵活性：为什么"改得动、换得掉"

独立部署

改一个服务只发布它自己，不需整体回归，发布更快、风险更隔离。

技术异构

新业务可用新语言/新存储，老服务不动，渐进式演进。

故障隔离

单点故障被隔离，配合熔断降级，局部坏不拖垮全局。

团队自治

小团队端到端负责一个服务（康威定律），并行不打架。

易替换

服务边界清晰，可整体重写/替换某服务而不动其他。

持续交付

每个小服务可独立 CI/CD，快速试错、快速迭代。

3.2 可扩展性：为什么"撑得住、花得省"

细粒度扩容

只对真正繁忙的服务（如秒杀订单）扩容，不必扩整站。

水平扩展

无状态服务加实例即可（Scale-out），近乎线性提升能力。

资源利用率高

不同服务负载错峰，按需分配，避免单体"为一点热点买整机"。

弹性伸缩

配合 K8s，按 CPU/流量自动扩缩，应对峰值与低谷。

无上限扩展

跨节点/跨机柜/跨地域部署，突破单机物理上限。

存储可扩展

各服务按数据特性选存储（KV/关系/时序），分库分表自然落地。

3.3 单体 vs 微服务：扩展方式对比（经典题型）

场景单体架构微服务架构
下单接口成为热点必须整体复制整套应用（含用不到的模块），浪费资源仅扩容"订单服务"实例，精准高效
流量高峰（大促）纵向升级单机 or 整体横向克隆，成本高热点服务自动扩容，闲时缩容，弹性省钱
引入新业务侵入大代码库，重编译重部署，风险高新建独立服务，即插即用，互不干扰
技术升级全栈绑定，升级牵一发动全身单服务可单独用新技术平滑迁移
灵活性提升要点：
  • 独立部署 → 发布快、风险小
  • 技术异构 → 渐进演进、老系统不推倒
  • 故障隔离 → 局部可用、降级保核心
  • 团队自治 → 并行开发、康威定律落地
可扩展性提升要点：
  • 细粒度扩容 → 只扩热点，省资源
  • 水平扩展 → 加实例线性提能力
  • 弹性伸缩 → 配合容器按需伸缩
  • 存储分治 → 各服务按需选型存储
客观提醒（考试也可能考权衡）：微服务不是银弹。它带来分布式复杂度： 网络延迟、数据一致性、运维（几十上百服务）、链路追踪、测试难度上升。 因此小系统/团队初期用单体更合适，当系统规模、团队规模、变更频率上来后再演进到微服务（"单体优先，按需拆分"）。
考试重点：① 灵活性 = 独立部署 + 技术异构 + 故障隔离 + 团队自治； ② 可扩展性 = 细粒度独立扩容 + 水平扩展 + 弹性伸缩 + 高资源利用率； ③ 与 2.2 关联：微服务是分布式思想在"应用架构"层的落地，其扩展同样依赖横向扩展（加节点）； ④ 权衡：微服务增加分布式复杂度，并非所有场景都适用。

★考试速记清单

  • 微服务定义＝将单体应用拆分为一组小型、松耦合、独立部署的服务，通过轻量通信协作，各服务自有数据。
  • 核心特性：单一职责、独立部署、松耦合、去中心化（数据+治理）、技术异构、故障隔离、轻量通信、可独立扩缩。
  • 全家桶组件：服务注册发现、API 网关、配置中心、服务通信、熔断限流（容错）、链路追踪、容器+K8s 编排、消息队列。
  • 分布式数据管理第一原则：Database per Service（每服务独立库，禁止跨库直访）。
  • 跨服务一致性方案：Saga（补偿回滚）、TCC（预留+确认/取消）、事件溯源、CQRS、消息队列最终一致； 多走 BASE/最终一致（与 2.2 的 CAP/AP 一致）。
  • 灵活性＝独立部署 + 技术异构 + 故障隔离 + 团队自治（改得动、换得掉）。
  • 可扩展性＝细粒度独立扩容 + 水平扩展 + 弹性伸缩 + 高资源利用率（撑得住、花得省）。
  • 权衡：微服务增加分布式复杂度（一致性/运维/延迟），小系统宜"单体优先、按需拆分"。
  • 与 2.2 关联：微服务是分布式思想在应用层的落地；Dubbo/Spring Cloud 等分布式服务框架支撑微服务； 其数据最终一致性与 CAP/BASE 一脉相承。
