6.3

一、基本概念总览：什么是身份、授权和访问管理（IAM）

6.3.1 身份、授权和访问管理（IAM）的定义

掌握
IAM（Identity and Access Management，身份与访问管理）= 一套确保"正确的人 / 服务，在正确的条件下，用正确的权限，访问正确的资源"的框架与体系。它由三大支柱构成：身份（Identity）、认证（Authentication）、授权（Authorization）。

理解 IAM 要抓住"一句总纲 + 三块拼图"：

  • 总纲："你是谁（身份）→ 证明你是谁（认证）→ 你能干什么（授权）"。
  • ① 身份（Identity）：为每个用户、设备、应用、服务分配一个唯一且可识别的"身份"（账号、角色、服务主体），是一切安全控制的锚点。
  • ② 认证（Authentication）：验证"声称的这个身份"确实是本人——解决"你是谁"的问题。
  • ③ 授权（Authorization）：在身份被确认后，决定"这个身份能做什么、能碰哪些资源"——解决"你能干什么"的问题。
  • 生活比喻：坐飞机——登机牌上的名字是身份，过安检刷身份证+人脸是认证，头等舱能进休息室、经济舱不能，就是授权。
  • 云上对应：一个 RAM 子用户（身份）→ 输入密码+短信验证码登录（认证）→ 被策略允许读取某 OSS 桶但不允许删除（授权）。

6.3.1（补）认证 vs 授权：最易混淆的一对概念

掌握
认证（Authentication）= "你是谁"（验证身份，常缩写为 AuthN）；授权（Authorization）= "你能做什么"（赋予权限，常缩写为 AuthZ）。先认证、后授权，二者顺序不可颠倒，且相互独立。
维度认证 Authentication（AuthN）授权 Authorization（AuthZ）
回答的问题"你是谁？是不是本人？""你被允许做什么？能访问哪份资源？"
发生时机登录 / 调用接口的第一步在认证通过之后
常见手段密码、指纹、短信码、MFA角色、策略、ACL（访问控制列表）、权限矩阵
失败表现拒绝登录（身份不成立）登录成功但操作被拒（没权限）
经典英文"Who are you?""What can you do?"
⚠ 考试易错点：很多人把"输入密码"叫做"授权"，这是错误的——输入密码是在认证；只有系统随后判断"该账号能不能删库"才叫授权。考题常混淆二者，务必分清"验证身份"和"赋予权限"。
6.3

二、身份认证（Authentication）：验证"你是谁"

6.3.2 身份认证的三大类因素（认证因子）

掌握
身份认证依据三类"因子"：① 你知道什么（知识因子，如密码/PIN）；② 你拥有什么（持有因子，如手机/硬件令牌/智能卡）；③ 你是什么（固有因子，如指纹/人脸/声纹）。单一因子叫单因素认证，两类及以上组合即构成 MFA（见第四节）。

逐一拆解三类因子（考试高频，会让你判断某个认证属于哪类）：

因子类别英文 / 别名典型例子特点
① 知识因子
Knowledge		你知道什么
What you know		口令、密码、PIN 码、安全问题答案最常用、最弱；易被钓鱼/撞库/泄露
② 持有因子
Possession		你拥有什么
What you have		手机（短信/TOTP App）、U 盾、智能卡、硬件令牌需物理持有；可能丢失/被 SIM 劫持
③ 固有因子
Inherence		你是什么
What you are		指纹、人脸、虹膜、声纹（生物特征）便捷难伪造；存在隐私与误识率
图 6-4（6.3）身份认证三大因素：知识 / 持有 / 固有
  • 判断练习："用指纹解锁手机"→ ③ 固有因子；"输银行卡密码"→ ① 知识因子；"收短信验证码"→ ② 持有因子（手机在你手上）。
  • 新趋势：业界正从"知识因子为主"转向"无密码（Passwordless）"，如 FIDO2/Passkey——直接用设备内置的生物识别+公私钥，密码本身不再传输，大幅降低钓鱼风险。

6.3.2（补）常见认证方式与协议

熟悉
认证协议解决"怎么安全地交换凭证并确认身份"：最基础的是"用户名+密码"；进阶有基于令牌的 Token 认证（如 JWT）、单点登录（SSO）、以及联合身份协议 SAML / OAuth 2.0 / OIDC（详见第六节）。
  • 静态口令：最常见的单因素认证，缺点是易弱口令、易泄露、易撞库。
  • 基于令牌（Token）：登录后服务端签发一个短期有效的令牌（如 JWT、访问令牌），后续请求携带令牌即可，避免反复传密码。
  • 证书 / 密钥对：机器与机器（服务间）常用——用私钥签名、公钥验签，无需人类输入密码（云上 AK/SK、SSH Key 即此类）。
⚠ 考试易错点：云环境里"长期 AccessKey/SecretKey"本质是静态凭证，一旦泄露危害极大。安全实践要求优先使用临时凭证（STS）和角色扮演，而非把长期密钥写死在代码里。
6.3

三、权限管理（Authorization）：决定"你能干什么"

6.3.3 授权模型：DAC / MAC / RBAC / ABAC

掌握
授权（Authorization）= 在身份被确认后，依据"策略/规则"决定其可执行的动作与可访问的资源。主流模型有：DAC（自主访问控制）、MAC（强制访问控制）、RBAC（基于角色的访问控制，云上最常用）、ABAC（基于属性的访问控制，最细粒度）。
模型核心思想例子适用
DAC
自主访问控制		资源拥有者自己决定把权限给谁文件右键"共享给某人"小型/个人
MAC
强制访问控制		系统按固定安全级别统一强制规定，用户无法自改军方机密分级，低密级不能读高密级高安全/政务
RBAC
基于角色
（⭐云上主流）		把权限"打包成角色"，给用户/服务分配角色"只读角色"只能看不能改；"管理员角色"全权企业/云
ABAC
基于属性		按"用户属性+资源属性+环境属性"动态算权限"仅工作时间内、来自公司 IP 的运维才能删库"细粒度/动态
  • RBAC 示例（最该记）：公司把权限拆成「只读」「开发」「运维管理员」三个角色；新来的小王被加进"只读"角色，他立刻拥有只读权限——不用逐条给他配资源。这就是 RBAC「角色 = 权限集合」的精髓。
  • ABAC 示例：同一个人，在公司内网+工作时间可被授权删除，深夜从境外 IP 登录则被拒绝。权限随"属性"动态变化。
⚠ 考试易错点：RBAC 的"R"是 Role（角色），不是 Rule。常考：云厂商的 IAM 控制台里你建立的是角色/策略，给用户绑定角色即可，而不是给用户逐个资源配权限——这正是 RBAC 相对于"逐用户配 ACL"的优势（好管理、不易错）。

6.3.3（补）最小权限原则（PoLP）

掌握
最小权限原则（Principle of Least Privilege, PoLP）= 每个身份只被授予"完成工作所必需的最小权限集"，不多给、不默认给、权限过期即回收。它是授权设计的第一原则，也是云安全合规的硬性要求（等保、GDPR 均强调）。
  • 做法：默认拒绝（deny by default），显式按需开通；避免直接给"管理员/FullAccess"这种大权限；定期审计并回收不再需要的权限（权限衰减）。
  • 为什么关键：一旦某账号被攻破，泄露面被限制在最小范围，避免"一个弱口令拖垮整个云账户"。
  • 反例（危险）：给一个只用来读日志的脚本授予 AdministratorAccess 全权限——脚本密钥泄露即等于交出整座云。
  • 正例：该脚本仅绑定"只读日志"角色，且用临时凭证，泄露后影响极小。
6.3

四、多因素认证（MFA）：给认证加一道保险

6.3.4 MFA 的定义与"多因素"的含义

掌握
MFA（Multi-Factor Authentication，多因素认证）= 在认证时要求同时提供"两类或以上不同类型因子"（通常至少来自知识/持有/固有中的两类），即使其中一类被攻破，攻击者仍因缺另一类而无法登录。它显著提升账号抗钓鱼、抗泄露的能力。

关键细节（考试常问）：

  • "多因素"必须跨"类型"：仅"密码 + 安全问题"仍是两类知识因子，不算真正的 MFA；必须混合不同类型（如 密码 + 手机验证码 = 知识+持有）。
  • 2FA ≠ 一定安全：两步验证（2FA）若两步都是同一类因子，安全增益有限；真正有效的是"跨因子组合"。
  • 价值：即便密码已泄露（撞库/钓鱼），没有第二因子攻击者依旧进不去——这是抵御"账户劫持"最有效的单点措施。
图 6-5（6.3）MFA = 两类不同因子叠加，破解一道仍有另一道
  • 实例：登录云控制台，先输密码（知识因子），再要求手机 TOTP 动态码或短信码（持有因子）。即便密码在别处泄露，攻击者没有你的手机，依旧进不去。
  • 考试典型题："仅使用密码 + 图形验证码"属于 MFA 吗？→ 不属于，两者本质都是"知识/系统挑战"类，未跨越因子类型；需叠加持有或固有因子。

6.3.4（补）MFA 的常见实现形式

熟悉
MFA 第二因子的常见落地：① 软件令牌（TOTP，如 Google Authenticator / 微软验证器，离线 30 秒滚动码）；② 短信 / 语音验证码（持有手机号）；③ 硬件令牌 / U 盾 / FIDO 安全密钥（U2F）；④ 推送确认（手机 App 弹出"是否允许登录"）；⑤ 生物识别 + 设备绑定（手机指纹解锁后授权）。
形式原理安全性评价
TOTP 软件令牌App 基于共享密钥+时间生成 6 位动态码较安全、离线可用；需保护好种子密钥
短信 / 语音码下发到注册手机便捷但可被 SIM 交换攻击拦截，安全性较弱
硬件令牌 / U2F物理密钥（如 YubiKey），基于公钥加密最强，抗钓鱼；需物理持有设备
App 推送确认手机收到登录请求，点击允许/拒绝体验好；依赖手机安全
⚠ 考试易错点：短信验证码 MFA 虽常见，但不是最安全的 MFA（存在 SIM 劫持风险）。在金融、核心云管理等高安全场景应优先采用硬件密钥（U2F/FIDO2）或 TOTP。考题若问"最抗钓鱼的 MFA"，答案是基于公钥的硬件安全密钥。
6.3

五、身份访问管理在云计算环境中的重要性

6.3.5 为什么云环境特别需要 IAM

掌握
在云环境中，IAM 不是"可选项"而是"地基"：云去边界化（访问来自任意地点）、多租户共享、责任共担、API 驱动运维、以及凭证泄露是头号威胁——这五点使"管好身份与权限"成为云安全的第一道、也是最关键的一道闸门。
云环境特征带来的安全挑战IAM 如何化解
去边界化没有固定内网边界，访问来自全球任意终端以"身份"代替"IP/位置"作为信任锚（身份即边界）
多租户共享同平台跑多家客户，越权即串门严格身份隔离 + 细粒度授权，防跨租户访问
责任共担"云中安全"归客户，配置权限属客户责任IAM 是客户侧最该自己把控的安全抓手
API 驱动一切操作经 API/密钥，凭证泄露=全网失守强制 MFA + 临时凭证 + 密钥轮换 + 最小权限
凭证泄露为头号威胁AK/SK 泄露常被用于挖矿、拖库、勒索IAM 集中管控身份、审计每一次访问
  • 呼应 6.1：在 6.1 列出的云安全头号威胁中，"配置错误"和"身份凭证泄露/弱认证"均排前列，而二者都直接落在 IAM 的管辖范围——可见 IAM 是云安全的"总开关"。
  • 真实事故：某公司将含长期 AK/SK 的代码传 GitHub，被扫描到后攻击者用其开通大量机器挖矿，账单飙升。若当时用了 IAM 最小权限 + 临时凭证 + MFA，损失可大幅降低。

6.3.5（补）"身份即边界"与零信任

熟悉
"身份即边界"（Identity as the New Perimeter）= 在云时代，不再依赖网络位置（IP/内网）判断可信，而是以"经过强认证的身份 + 当前上下文"作为访问决策的核心依据。这与"零信任（Zero Trust：默认不信任、持续验证）"一脉相承，而 IAM 正是零信任的落地支撑。
  • 传统思路："在内网 = 可信"，靠防火墙划边界 → 云上边界消失，思路失效。
  • 云思路："无论你在哪，都必须证明身份、且权限合规才放行"，每一次访问都重新评估。这就是 IAM 在云中"顶替防火墙成为新边界"的含义。
图 6-6（6.3）从"网络边界"到"身份即边界 / 零信任"，IAM 是承载体
⚠ 考试易错点：说"云安全不再需要边界"是错的——准确说法是传统"网络位置边界"失效，取而代之的是"身份边界"。IAM 让身份成为新的信任锚点。
6.3

六、身份访问管理在云计算环境中的实现方式

6.3.6 IAM 系统的整体架构（四大组件）

熟悉
一个完整的云 IAM 实现通常包含四块：① 身份目录（Identity Store，集中管理用户/角色/服务主体）；② 认证服务（Authentication，校验凭证、签发令牌、强制 MFA）；③ 授权引擎（Authorization，依据策略判定允许/拒绝）；④ 审计日志（Accounting/Audit，记录"谁、何时、对什么、做了什么"）。即常说的 IAAA（Identification 身份标识 / Authentication 认证 / Authorization 授权 / Accountability 可审计）。
图 6-7（6.3）IAM 访问流程：请求 → 认证 → 授权 → 资源，全程审计留痕
  • 流程串联：用户请求 → 认证服务核对密码+MFA，签发短期令牌 → 授权引擎按 RBAC 策略判断"该角色能否读此资源" → 允许则访问，同时审计日志记录此次行为，便于事后追溯与异常发现。

6.3.6（补）单点登录（SSO）、联邦身份与标准协议

熟悉
为兼顾"安全"与"好用"，云 IAM 普遍采用：① SSO（单点登录，一次登录可访问多个系统）；② 联邦身份（Federation，用企业已有身份源如 AD/钉钉/企业微信直接登录云，无需在云上另建账号）；③ 标准协议 SAML 2.0（企业 SSO 传统标准）、OAuth 2.0（授权委托，常用于 App 授权）、OIDC（在 OAuth 上叠加身份认证，现代主流）。
协议定位典型场景
SAML 2.0基于 XML 的跨域身份断言（认证为主）企业员工用公司账号登录云控制台
OAuth 2.0授权委托框架（"代我访问某资源"）第三方 App 申请"读取你的头像"
OIDCOAuth 2.0 之上加身份认证（ID Token）现代 Web/移动端登录（如微信/Google 登录）
  • SSO 好处：员工只需记一套企业密码；离职时在企业侧停用账号，云上权限同步失效，避免"影子账号"残留。
  • 联邦身份示例：公司用 Azure AD 管员工，配置联合后，员工用 AD 账号+企业 MFA 直接登云控制台，云上不再单独存一份密码。
⚠ 考试易错点：OAuth 2.0 本质是授权协议不是认证协议；要做"身份认证"应在其上加 OIDC。考题常混淆"OAuth 用来登录"——更准确是"OIDC（基于 OAuth）用来认证登录"。

6.3.6（补）主流云平台 IAM 的落地示例

了解
各云厂商对 IAM 的命名与实现内核一致：AWS = IAM（用户/组/角色 + 策略 + MFA + STS 临时凭证）；阿里云 = RAM（资源访问管理，用户/角色/权限策略）；华为云 = IAM（用户/用户组/委托 + 策略）；腾讯云 = CAM。核心都围绕"身份 + 认证(MFA) + 授权(策略/RBAC) + 审计"。
云厂商IAM 产品名关键能力对照
AWSIAM用户/组/角色；JSON 策略；MFA；STS 临时凭证；角色扮演（跨账号）
阿里云RAM子用户/用户组/角色；权限策略；MFA；RAM 角色（ECS 实例扮演）
华为云IAM用户/用户组/委托；细粒度策略；MFA；企业联邦（ADFS）
腾讯云CAM子账号/角色；策略；MFA；联合身份
  • 统一理解：不管是哪个云，考题给的"用户/角色/策略/MFA/临时凭证"指的都是同一套 IAM 逻辑，换名字不影响答题——抓住"身份、认证、授权、审计"四要素即可。

6.3.6（补）审计、监控与最佳实践（落地闭环）

掌握
IAM 落地的安全闭环 = 强认证（全量 MFA）+ 最小权限（RBAC/默认拒绝）+ 临时凭证（STS、避免长期密钥）+ 密钥定期轮换 + 集中审计与异常告警（如异地登录、高频失败、越权尝试）+ 定期权限复查回收。六点缺一不可。
  • ① 全员 MFA：尤其管理员与高权限账号强制 MFA。
  • ② 最小权限：用角色而非直接 FullAccess；默认拒绝。
  • ③ 临时凭证优先：服务间用角色扮演拿 STS 临时令牌，避免长期 AK/SK 写代码。
  • ④ 密钥轮换：长期密钥定期更换、泄露即吊销。
  • ⑤ 审计告警：开启云审计（如 CloudTrail / 操作审计），对异常行为实时告警。
  • ⑥ 权限复查：定期清理离职/闲置账号与多余权限（权限衰减）。
⚠ 考试易错点（综合必考）："买了云就安全了"是错的——IAM 的正确配置是客户责任（呼应 6.1 责任共担）。把长期密钥硬编码到代码、给脚本配管理员权限、高权账号不开 MFA，都是典型的"客户侧配置失误"，属于可避免的安全事故。
  • 一句话总结实现方式：用"集中身份目录 + 强认证(MFA) + 基于角色的细粒度授权 + 临时凭证 + 全程审计"这一整套机制，把云上的"谁能进、进后能做什么、做了什么"完全管起来——这就是 IAM 在云计算中的实现方式。
