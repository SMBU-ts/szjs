6.1

云安全的概念及重要性

一、云安全的定义与常见威胁

6.1.1 云安全的定义

熟悉
云安全 = 保护云计算环境（数据、应用、平台、基础设施、账号）的机密性、完整性、可用性（CIA三性），并融合云计算特有风险（多租户、虚拟化、责任共担）而形成的安全体系。

云安全不是某一款产品，而是一套"技术 + 策略 + 运维"的组合：既包括传统信息安全（网络安全、主机安全、数据安全），又叠加了云特有的责任共担、多租户隔离、弹性资源等新问题。

  • 传统安全 vs 云安全：传统安全以"边界防火墙"为核心；云安全因为资源弹性伸缩、边界模糊，更强调"身份即边界"和"零信任"。
  • 范围示例：云安全既管"别人能不能偷看你的数据库"（机密性），也管"数据被改了没"（完整性），还管"服务卡顿打不开"（可用性）。

6.1.2 常见云安全威胁（CSA 云安全威胁清单）

掌握
最高频的云威胁：配置错误（Misconfiguration）、身份凭证泄露/弱认证、不安全的接口与 API、账户劫持、内部威胁、共享技术漏洞、数据泄露与丢失。
威胁说明典型场景
配置错误存储桶/安全组/端口被错误开放为公网（云上"头号"事故源）对象存储设为公开可读，导致用户数据被全网爬取
身份凭证泄露 / 弱认证密钥、密码、AK/SK 泄露，无 MFA 保护开发者把 AccessKey 提交到 GitHub，被恶意扫描利用挖矿
不安全的接口/APIAPI 未鉴权、未限流、存在越权漏洞越权接口可遍历他人订单 ID 获取隐私
账户劫持钓鱼/撞库夺取管理员账号钓鱼邮件骗取控制台登录，删库勒索
内部威胁（恶意/失误）内部人员越权访问或误操作离职员工带走数据，或误删生产库
共享技术漏洞虚拟化/容器隔离被突破，跨租户越权同宿主机的邻居通过侧信道或漏洞读到你的内存
数据泄露 / 数据丢失被窃取或误删、未备份勒索软件加密数据；误删且无备份
拒绝服务（DoS/DDoS）流量打满导致服务不可用大规模请求冲垮 Web 入口
滥用云服务用云资源做攻击跳板（挖矿、钓鱼）攻击者用盗用的账号发起对外攻击
  • 配置错误示例：某公司将云数据库 3306 端口对 0.0.0.0/0 开放且无密码，被勒索组织拖库——这是"客户侧责任"，CSP 不背锅。
  • 凭证泄露示例：把长期有效的 Secret Key 写进前端代码，等于把家门钥匙挂在门口。

二、云计算环境中安全问题的复杂性与多样性

6.1.3 复杂性与多样性的来源

熟悉
云安全"更复杂"的根本原因：边界消失、多租户共享、责任共担、资源弹性、合规跨境、攻击面叠加（虚拟化+容器+API+供应链）。
  • 边界模糊：传统"内网可信"假设失效，访问来自任意终端/任意地点 → 必须"零信任"（默认不信任、持续验证）。
  • 多租户隔离：同一物理机跑多家客户的数据，隔离一旦失效就会"串门"，对底层虚拟化/容器安全提出极高要求。
  • 责任共担：安全职责在 CSP 与客户之间分割，双方都以为对方负责 → 出现"责任真空"。
  • 弹性与动态：资源随时创建/销毁，资产盘点、日志审计、配置基线难以稳定，影子 IT（未纳管资源）丛生。
  • 合规与数据主权：数据可能落在境外机房，要同时满足等保、GDPR、《数据安全法》《个人信息保护法》等多套法规。
  • 攻击面叠加：IaaS 的虚拟化、PaaS 的运行时、SaaS 的接口、加上第三方依赖/供应链，攻击面比传统 IT 更广。
  • 多样性示例：同样叫"上云"，用 IaaS 自己装系统（客户责任大）和用 SaaS（几乎全交给厂商）面临的安全工作天差地别——这就是"多样性"。

三、云安全对于云计算的重要性

6.1.4 为什么云安全是云计算的"生命线"

熟悉
没有安全就没有信任，没有信任就没有上云——云安全决定了云计算能否被采用、能否合规、能否持续运营。
  • 数据是核心资产：云上集中存放大量敏感数据，一旦泄露代价极高（声誉、罚款、诉讼）。
  • 业务连续性依赖可用性：云是业务关键底座，DDoS/勒索导致中断即直接损失营收。
  • 合规硬约束：金融、政务、医疗等行业上云必须满足等保/行业监管，否则不能上线。
  • 信任基础：企业是否敢把核心系统搬到云，取决于对 CSP 安全能力的信任。
⚠ 考试易错点：云安全不是"买了云就自动安全"。CSP 负责"云本身安全"（基础设施），客户负责"云中安全"（配置、数据、身份）——安全是双方共同责任。
6.2

常见安全防护措施及相关安全策略

一、云计算核心架构安全（纵深防御）

6.2.1 核心架构安全分层

熟悉
云安全遵循"纵深防御（Defense in Depth）"：从物理层 → 网络层 → 主机/计算层 → 应用层 → 数据层 → 身份层 → 安全运维，层层设防、任一单层被破仍有其他层兜底。
层级防护重点常见措施
物理安全机房、电力、防灾门禁、监控、冗余供电（多为 CSP 负责）
网络安全隔离与访问控制VPC 私有网络、安全组、微隔离、WAF、DDoS 防护
主机/计算安全系统与应用运行环境镜像加固、补丁、堡垒机、主机入侵检测 HIDS
应用安全代码与接口安全开发生命周期（SDLC）、API 鉴权、漏洞扫描
数据安全数据全生命周期加密、脱敏、备份、DLP 数据防泄露
身份安全人/程序身份IAM、MFA、最小权限、SSO
安全运维监测与响应日志审计、SIEM/SOC、态势感知、应急响应
  • 纵深防御示例：即使黑客拿到一个 Web 应用权限（应用层破），仍要面对网络微隔离（拿不到数据库网段）、数据加密（读到的也是密文）、审计告警（行为被记录）——多层拦截。

二、责任共担模型（Shared Responsibility）

6.2.2 云安全责任如何划分

掌握
核心规则：CSP 负责"云本身的安全"（Hypervisor、网络、物理）；客户负责"云中的安全"（操作系统、应用、数据、身份与访问配置）。服务模型越往上（IaaS→PaaS→SaaS），CSP 承担越多，客户责任越少。
图 6-1 责任共担模型：越往上（SaaS）CSP 责任越大
⚠ 考试易错点：无论哪种服务模型，"数据加密与客户端配置、身份管理"始终属于客户责任——CSP 不会替你设好密码和权限。

三、IaaS / PaaS / SaaS 安全防护措施与策略要求

6.2.3 三类服务模型的安全重点

掌握
IaaS 重"系统层"，PaaS 重"应用与配置"，SaaS 重"使用与账号"——防护重心随责任转移而不同。
维度IaaS（基础设施）PaaS（平台）SaaS（软件）
客户主要
责任面		Guest OS、应用、数据、网络 ACL应用代码、数据、配置账号、权限、使用配置、DLP
关键防护措施镜像/主机加固、及时打补丁、安全组最小化、堡垒机、磁盘加密、操作审计安全 SDLC、依赖/组件漏洞扫描、密钥管理、API 安全、配置基线SSO、强制 MFA、最小权限、数据防泄露、登录与操作审计
策略要求禁止 0.0.0.0/0 全开；定期漏洞扫描；变更需审批默认安全配置；密钥不得硬编码；CI/CD 安全门禁账号生命周期管理（入职/离职回收）；外发内容管控
  • IaaS 示例：自己用云服务器搭网站——你得自己装防火墙、打系统补丁、管数据库密码。
  • PaaS 示例：用云上的数据库/函数计算——你只需管好访问密钥和 SQL 权限，底层系统由厂商管。
  • SaaS 示例：用在线办公/邮箱——你重点管好员工账号、开启 MFA、限制文件外发。

四、不同云计算应用的安全策略与部署重点

6.2.4 按业务场景定策略

熟悉
没有"放之四海皆准"的安全策略，应按应用特征（是否对外、是否含敏感数据、是否强合规）确定部署重点。
应用类型部署重点
对外 Web / 电商WAF + DDoS 防护 + HTTPS + 防爬防刷 + 应用层限流
数据密集型 / 大数据静态加密 + 备份容灾 + 脱敏 + 访问分级 + 跨区域复制
金融 / 政务（强合规）等保三级 + 专属/私有云或专区 + 密钥自管(BYOK) + 全量审计
IoT / 边缘设备身份认证 + 设备证书 + 网关加密 + 固件签名校验
DevOps / 研发CI/CD 安全门禁 + 密钥不进代码库 + 镜像扫描 + 最小权限流水线

五、如何评估 CSP（云服务提供商）安全性

6.2.5 评估 CSP 安全性的维度

掌握
看"证书 + 透明度 + 数据主权 + SLA + 加密可控 + 事件响应"六方面；优先选择有第三方审计背书、合规齐全的厂商。
  • 合规认证：ISO 27001、SOC 2 Type II、PCI DSS、国内等保三级/四级、CSA STAR——这些是"第三方替你审过"的依据。
  • 安全透明度：是否公开安全白皮书、合规报告（如 SOC 2 报告）、是否接受渗透测试与漏洞披露。
  • 数据位置与主权：数据中心地域是否可选、是否满足数据不出境/本地化要求。
  • SLA 与持久性：可用性 SLA（如 99.95%）、数据持久性（如 99.999999999%）、故障赔付条款。
  • 加密与密钥控制：是否支持客户自管密钥（BYOK / HYOK）、是否提供 KMS/HSM。
  • 事件响应：是否有明确的安全事件通知时效（如 24 小时内告知）、应急与溯源能力。
  • 评估示例：金融客户选型时，先卡"是否具备等保三级 + 金融云专区 + 支持 BYOK"，再比 SLA 与事故赔付，最后看透明度报告。
6.3

身份、授权和访问管理（IAM）

一、基本概念：认证 · 授权 · MFA

6.3.1 身份认证 / 权限管理 / MFA

掌握
认证（Authentication）回答"你是谁"；授权（Authorization）回答"你能干什么"；MFA（多因素认证）用两种以上因素证明身份，防止单点凭证泄露。
概念本质问题常见手段
身份认证
(Authentication)		你是谁？密码、数字证书、生物特征、硬件 Token、单点登录
权限管理 / 授权
(Authorization)		你能做什么？RBAC（基于角色）、ABAC（基于属性）、最小权限、默认拒绝
MFA 多因素认证再加一道保险知识(密码) + 持有(手机/令牌) + 固有(指纹/人脸)
  • 认证三要素（MFA 的"因素"）：① 你知道的（密码/PIN）；② 你拥有的（手机/硬件 Key/U 盾）；③ 你本身的（指纹/人脸/声纹）。满足两类即"多因素"。
  • 最小权限原则：只给完成工作所必需的最小权限，默认拒绝一切未明确放开的访问。
  • MFA 示例：登录时输密码（知识）+ 手机验证码/Authenticator 动态码（持有），即使密码泄露也登不进。
  • RBAC 示例："只读分析师"角色只能查数据不能删，新员工按角色批量授权，离职一键回收。

二、IAM 在云计算环境中的重要性

6.3.2 为什么云上 IAM 是"第一道防线"

熟悉
云时代"身份即边界"：传统防火墙守不住分散访问，凭证泄露又是头号云威胁，因此管好"谁能访问什么"比以往任何时候都关键。
  • 云资源由 API/控制台远程访问，没有固定内网边界 → 身份成为唯一可靠的访问控制点。
  • 大量攻击（账户劫持、AK 泄露）都从"冒用合法身份"入手，IAM 是阻断此类攻击的核心。
  • 集中式 IAM 带来统一认证、统一授权、统一审计，满足合规对"账号可追溯"的要求。

三、IAM 的实现方式

6.3.3 云中 IAM 的落地手段

熟悉
主流实现：目录服务(AD/Entra ID) + SSO(单点登录) + 联合身份(Federation) + 角色/策略(临时凭证 STS) + 特权访问管理(PAM) + 零信任持续验证。
图 6-2 典型云身份流程：SSO 统一认证 + MFA 加强 + 临时凭证(STS)访问云资源
  • SSO（单点登录）：一次登录通行多个系统，常用 SAML、OIDC 协议，减少密码散落。
  • 联合身份（Federation）：用企业自有 IdP（如 AD）信任云厂商，员工用公司账号登云，离职即失效。
  • 角色与 STS 临时凭证：程序/人临时代入角色拿到短期有效的临时密钥，避免长期 AK 泄露风险。
  • PAM（特权访问管理）：对管理员等高权限账号做审批、录像、时限控制。
  • 零信任："从不信任、持续验证"，每次访问都重新评估身份、设备、环境风险。
  • 最佳实践示例：用企业微信/AD 做 SSO 登录云控制台，强制 MFA，给运维开"仅工作时间、仅特定网段、需审批"的临时角色，全程留痕。
6.4

数据加密与密钥管理

一、数据在存储、传输、使用中应用加密的必要性

6.4.1 加密三态：静态 / 传输中 / 使用中

掌握
数据有"三种状态"需分别防护：静态（存储）防磁盘/备份泄露；传输中（网络）防窃听/中间人；使用中（计算/内存）防运行时泄露——"全态加密"才是真正闭环。
图 6-3 数据加密三态：覆盖"存、传、算"才能形成闭环
  • 静态加密必要性：磁盘/备份盘丢失或被盗、存储桶误公开、内部人员越权读取时，密文无法被直接利用。
  • 传输加密必要性：公网传输若明文，易被中间人窃听、篡改、重放；TLS 保证"只有收发双方看得懂"。
  • 使用中加密必要性（进阶）：数据在计算/内存时是明文，机密计算（如可信执行环境 TEE）让数据"用的时候也不裸奔"，是前沿重点。
⚠ 考试易错点："传输加密"指网络传输用 TLS，不等于"存储加密"；两者都要做，不能互相替代。

二、常见加密方法

6.4.2 对称 / 非对称 / 哈希 / 信封加密

掌握
对称加密快（AES/SM4）用于大数据；非对称加密(RSA/ECC/SM2)用于密钥交换与签名；哈希(SHA/SM3)用于完整性；实际系统用"信封加密"把三者结合。
类型特点代表算法用途
对称加密加解密用同一把密钥，速度快AES-256、国密 SM4大批量数据静态加密、磁盘加密
非对称加密公钥加密/私钥解密，或私钥签名/公钥验签RSA、ECC、国密 SM2密钥协商、数字签名、证书
哈希/摘要单向不可逆，固定长度指纹SHA-256、国密 SM3完整性校验、口令存储（加盐哈希）
信封加密数据密钥(DEK)加密数据，主密钥(CMK)加密 DEKAES + KMS云上规模化加密（见下节）
  • 为什么需要非对称 + 对称结合？非对称安全但慢，不适合加密大文件；所以先用非对称"安全地交换"一把对称密钥，再用这把对称密钥高速加密数据（TLS 正是如此）。
  • 国密算法：国内合规常用 SM2（非对称）/SM3（哈希）/SM4（对称），金融、政务上云常要求支持国密。
  • 信封加密示例：上传文件时，系统用随机生成的"数据密钥"把文件 AES 加密（快）；再用 KMS 里的"主密钥"把该数据密钥加密后和密文一起存。解密时反向操作——主密钥永不离开 KMS，安全性与性能兼得。

三、密钥管理（KMS / HSM / BYOK）

6.4.3 密钥比数据更该被保护

熟悉
"密钥管理不好，加密等于没加密"：密钥需集中管理(KMS)、硬件保护(HSM)、定期轮换、分级隔离，并支持客户自管(BYOK)。
  • KMS（密钥管理服务）：集中生成、存储、轮换密钥，主密钥(CMK)不离开硬件边界；应用只调 API 加解密。
  • HSM（硬件安全模块）：专用硬件保护密钥，防提取、防篡改，金融级高安全场景使用。
  • 密钥轮换：定期更换密钥，降低单把密钥泄露的影响面。
  • 分级与隔离：主密钥(CMK)与数据密钥(DEK)分离；不同业务用不同密钥，避免"一把钥匙开所有门"。
  • BYOK / HYOK：客户自带密钥(BYOK)或持有自己密钥(HYOK)，云厂商看不到明文密钥，满足强合规与"密钥自管"诉求。
  • BYOK 示例：银行把自有的主密钥导入云 KMS，云上数据用这把密钥加密；即使云厂商被攻破，没有银行的密钥也解不开数据。
  • 轮换示例：每年自动轮换一次主密钥，旧密文仍可用旧密钥解密、新数据用新密钥——平滑无感。
