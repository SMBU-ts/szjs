一、Web 服务的定义与基本特性

定义：Web 服务（Web Service）是一种通过网络（通常是 Internet/Intranet）实现机器对机器（M2M）互操作的软件系统。它对外暴露一个可被机器处理的接口描述（如 WSDL），调用方通过标准化的消息格式（典型为 SOAP/XML 或 REST/JSON）与其交互。

1.1 本质

可以把 Web 服务理解为「部署在 Web 上的、可程序化调用的功能单元」——它把一段业务逻辑（如查询天气、扣款、查库存）封装起来，让不同平台、不同语言编写的程序都能像调用本地函数一样远程调用它。

1.2 基本特性

  • 互操作性平台无关、语言无关：.NET 程序可调用 Java 服务，只要遵循相同标准。
  • 松耦合服务端与客户端可独立演化，只要接口契约不变，内部实现可自由替换。
  • 自描述 / 契约化通过 WSDL（SOAP）或 OpenAPI（REST）描述接口、参数与返回值，调用方无需看源码即可对接。
  • 基于标准协议依托 XML、HTTP、SOAP、WSDL、UDDI 等开放标准，不被厂商锁定。
  • 可组合性多个原子服务可编排组合成更复杂的业务流程（服务编排 / BPM）。
  • 封装性只暴露接口，隐藏内部实现细节与数据结构。
  • 可寻址服务可通过 URI / 注册中心被发现与定位。
💡 一句话记忆Web 服务 = 用标准协议 + 机器可读描述，让异构系统互通的「网络函数」。

二、Web 服务的核心组件

以最经典的 SOAP Web 服务技术栈为例，核心组件自底向上构成一条完整的「通信链路」：

图 1 · 经典 SOAP Web 服务技术栈：自顶向下依赖，最底层以 XML 承载、通过 HTTP 等传输

2.1 各组件职责

组件英文 / 全称作用
XMLeXtensible Markup Language平台中立的数据表示格式，是 SOAP 消息的载体
SOAPSimple Object Access Protocol基于 XML 的消息封装协议，定义「请求/响应」的信封结构
WSDLWeb Services Description Language用 XML 描述服务的「地址、操作、参数、数据类型」契约
UDDIUniversal Description, Discovery and Integration服务注册中心，供提供者发布、请求者查找服务
传输协议HTTP / SMTP / JMS / TCP承载 SOAP 消息的网络通道（Web 服务中最常用 HTTP）
🔑 REST 的核心组件（对照）对 RESTful 而言，核心组件更轻量：资源（Resource） + URI + HTTP 方法（GET/POST/PUT/DELETE） + 表示（Representation，多为 JSON） + 无状态通信。不需要 WSDL/UDDI/SOAP 这套重型栈。

三、Web 服务的工作流程

SOAP Web 服务遵循经典的 「发布 — 查找 — 绑定」（Publish-Find-Bind）三角模型，涉及三个角色：

  • 服务提供者（Service Provider）：拥有并部署服务的一方。
  • 服务注册中心（Registry，如 UDDI）：存放服务描述的目录。
  • 服务请求者（Service Requester）：调用服务的一方。
图 2 · Web 服务「发布—查找—绑定」工作流程

3.1 步骤拆解

  1. 发布（Publish）：提供者将 WSDL 描述文件发布到 UDDI 注册中心。
  2. 查找（Find）：请求者向注册中心查询所需服务的描述与端点地址。
  3. 绑定 / 调用（Bind）：请求者根据 WSDL 构造 SOAP 消息，通过 HTTP 发送到服务提供者，服务执行后返回 SOAP 响应。
⚙️ REST 的工作流程（简化）REST 没有 UDDI 注册环节：客户端直接通过已知 URI + HTTP 方法向服务端发起请求，服务端返回资源的表示（如 JSON）。流程即：客户端请求 URI → 服务端定位资源 → 返回表示，本质是「请求—响应」两步，远比 SOAP 三角模型轻量。

四、SOAP（简单对象访问协议）

SOAP 是一种基于 XML 的、用于交换结构化信息的轻量级协议。注意名为「简单对象访问协议」，但它既不简单、也不限于对象访问——它是一套严格的消息格式规范。SOAP 本身只定义消息结构，传输可绑定到 HTTP、SMTP、JMS、TCP 等。

4.1 基本结构（SOAP 信封）

每条 SOAP 消息都是一个 Envelope（信封），内部包含可选的 Header 与必需的 Body：

图 3 · SOAP 消息信封结构
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Header>
    <Auth>token123</Auth>          <!-- 可选：认证、事务等 -->
  </soap:Header>
  <soap:Body>
    <GetPrice>
      <Item>Book-001</Item>     <!-- 业务请求数据 -->
    </GetPrice>
    <!-- 出错时返回 <soap:Fault> ... </soap:Fault> -->
  </soap:Body>
</soap:Envelope>
元素是否必需说明
Envelope必需根元素，标识这是一条 SOAP 消息
Header可选扩展信息：安全令牌、事务 ID、路由路径等
Body必需真正的业务负载（调用的方法与参数 / 返回结果）
Fault可选错误信息容器：code、string、actor、detail

4.2 应用场景

  • 企业级 B2B 集成跨企业、跨系统的严谨数据交换（如供应链、ERP 对接）。
  • 金融 / 支付 / 银行需要强事务一致性、内置安全（WS-Security）、正式契约的高价值交易。
  • 遗留系统打通把老旧系统封装成 WS，供新系统以标准方式调用。
  • 需要正式契约与版本治理接口变更需严格管控、可追溯的场景。
✅ 优点
  • 标准化、跨平台、跨语言
  • WSDL 提供正式契约，机器可读、可代码生成
  • 内置安全/事务标准（WS-Security、WS-AtomicTransaction）
  • 强类型、结构严谨，错误通过 Fault 规范处理
  • 可绑定多种传输协议（不限于 HTTP）
❌ 缺点
  • XML 冗余，消息体大、带宽与解析开销高
  • 协议复杂、学习曲线陡、开发调试困难
  • 与 WSDL 紧耦合，灵活性差
  • 性能较低，不适合高并发轻量场景
  • 对简单 CRUD 而言「杀鸡用牛刀」

五、RESTful（表征性状态转移）Web 服务

REST 不是协议，而是一种架构风格，由 Roy Fielding 于 2000 年提出。它把一切都抽象为资源（Resource），通过 URI 定位、用统一的 HTTP 方法操作、以某种表示（如 JSON）在客户端与服务端之间转移状态。

5.1 六大设计原则（约束）

约束含义考试要点
1. 客户端-服务器分离
(Client-Server)		前端与后端职责分离，可独立演化关注点分离，提升可移植性
2. 无状态
(Stateless)		每个请求必须自带全部所需信息，服务端不保存客户端会话状态服务端无会话上下文，利于横向扩展
3. 可缓存
(Cacheable)		响应须标明是否可缓存，减少重复请求借助 HTTP 缓存头提升性能
4. 统一接口
(Uniform Interface)		REST 的核心，含 4 个子约束（见下）解耦架构的关键
5. 分层系统
(Layered System)		可插入代理、网关等中间层，客户端透明提升可伸缩性与安全性
6. 按需代码
(Code-On-Demand, 可选)		服务端可下发可执行脚本（如 JS）到客户端唯一可选约束

5.2 统一接口的四个子约束

  1. 资源由 URI 标识：每个资源有唯一地址，如 /users/1001。
  2. 通过表示操作资源：客户端拿到的是资源的「表示」（JSON/XML），修改表示即修改资源。
  3. 自描述消息：消息自带足够元信息（如 Content-Type），无需额外文档即可理解。
  4. 超媒体驱动应用状态（HATEOAS）：响应中嵌入可进一步操作的链接，客户端按需导航。

5.3 RESTful 设计实践

图 4 · REST 统一接口三要素：URI 定位资源 + HTTP 方法操作 + 表示承载状态
  • 资源用名词，不用动词 正确：GET /orders；错误：GET /getOrders。
  • 用 HTTP 方法表达动作：
方法语义对应操作幂等
GET读取资源查是
POST新建资源增否
PUT整体替换资源改（全量）是
PATCH部分更新资源改（增量）否
DELETE删除资源删是
  • 用 HTTP 状态码表达结果 200 成功、201 已创建、400 请求错误、401/403 未认证/无权限、404 不存在、500 服务端错误。
  • 无状态 每次请求携带完整凭证（如 Token），服务端不存会话。
  • 表示优先 JSON 轻量、易解析，已成为事实标准（也可 XML）。
# 获取用户
GET /users/1001  →  200 OK  { "id":1001, "name":"张三" }

# 创建订单
POST /orders     →  201 Created  { "id":77, "amount":99 }

# 删除用户
DELETE /users/1001  →  204 No Content

六、REST 安全性

REST 本身是无状态架构，没有内置的安全协议，安全需由传输层 + 应用层机制共同保障。以下为考试高频要点：

安全维度常用机制说明
传输安全HTTPS / TLS加密传输内容，防窃听、防中间人篡改（REST 安全基石）
身份认证OAuth 2.0、JWT（Bearer Token）、API Key、OpenID Connect无状态场景用令牌（Token）代替服务端 Session
授权 / 访问控制Scope、RBAC、ABAC控制「能访问哪些资源、能做哪些操作」
输入校验参数白名单、类型校验防 SQL 注入、XSS、XML/JSON 注入
限流 / 防刷Rate Limiting、Throttling防 DoS、暴力破解、资源耗尽
跨域安全正确配置 CORS限定可信来源，避免任意站点调用
审计与监控日志、告警记录访问、异常行为可追溯
🔐 关键对比：REST vs SOAP 的安全思路
  • SOAP：在协议层内置 WS-Security（XML 数字签名、加密、令牌），安全与消息绑定，即便走非 HTTPS 也能端到端保护。
  • REST：安全依赖外部标准——靠 HTTPS 保传输、靠 OAuth 2.0 / JWT 保身份，是「约定俗成」而非协议强制。
⚠️ 考试提示REST 强调无状态，因此不能用服务端 Session 维持登录，必须靠每次请求携带的 Token（如 JWT）来识别身份。这也是 REST 易水平扩展的原因。

七、REST 与 SOAP 异同比较

7.1 相同点（异中有同）

  • 都用于跨网络、跨平台的机器间通信，实现系统互操作。
  • 都可通过 HTTP 传输（也可承载于其他协议）。
  • 都采用请求/响应模型，都支持 XML 作为数据格式。
  • 都可用于构建分布式、松耦合的服务架构。

7.2 不同点（核心差异）

比较维度SOAPREST
本质一种协议（Protocol）一种架构风格（Architecture）
消息格式仅 XMLJSON / XML / HTML 等（多用 JSON）
接口契约正式 WSDL 契约通常无强制契约（常用 OpenAPI/Swagger 描述）
耦合度与 WSDL 紧耦合松耦合
状态可支持有状态设计为无状态
传输HTTP / SMTP / JMS / TCP 皆可通常基于 HTTP
性能XML 重、较慢、开销大轻量（尤其 JSON）、更快
安全内置 WS-Security 等标准依赖 HTTPS + OAuth/JWT 等外部机制
错误处理规范化的 <soap:Fault>HTTP 状态码（200/404/500…）
缓存不易缓存借 HTTP 缓存机制天然可缓存
复杂度 / 学习成本高低
典型场景企业 B2B、金融支付、事务性、强契约Web / 移动端、公开 API、轻量 CRUD
🎯 选型口诀要严谨契约、事务安全、跨协议选 SOAP；要轻量、高性能、易用、面向 Web/移动选 REST。当今互联网公开 API 绝大多数采用 REST（JSON）。
