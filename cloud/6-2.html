6.2 常见安全防护措施及相关安全策略

第6章 云计算安全 · 核心架构安全 | 责任共担 | IaaS/PaaS/SaaS 防护 | 应用安全策略 | 评估 CSP 安全性

一、云计算核心架构安全 掌握

1.1 纵深防御（Defense in Depth）

纵深防御是云计算安全的最核心指导思想：在网络的多个层次上部署重叠的安全控制，使单一层次被突破后仍有后续防线。

纵深防御通常由以下七层组成，从左到右由外向内形成防护金字塔：

第1层 物理安全 → 数据中心门禁、监控、电力冗余、物理隔离
第2层 网络边界 → 防火墙、WAF、DDoS 清洗、入侵检测系统（IDS/IPS）
第3层 主机/虚拟化 → 主机安全 agent（HIDS）、漏洞扫描、基线检查、防病毒
第4层 身份与访问 → MFA、IAM（最小权限）、SSO、条件访问策略
第5层 应用安全 → 代码审计、WAF、API 网关鉴权、RASP
第6层 数据安全 → 加密（静态+传输+使用中）、DLP、密钥管理 KMS
第7层 监控与响应 → 安全信息和事件管理（SIEM）、日志审计、威胁情报、SOAR 自动化响应

1.2 零信任架构（Zero Trust Architecture）

核心原则："从不信任，始终验证"。不因为设备位于内网就默认信任，每一次访问请求都必须经过认证和授权。

零信任三大支柱：

  • 微隔离（Micro-Segmentation）：将数据中心网络划分为极小的安全区，每个工作负载之间的流量都必须经过策略控制。
  • 持续验证：不只是登录时验证一次，而是持续评估用户行为、设备健康度、访问上下文，异常即阻断。
  • 最小权限：用户/服务仅被授予完成任务所需的最小权限，且权限动态调整、定期回收。

1.3 安全即代码（Security as Code）与 DevSecOps

将安全策略、检查规则、配置基线以代码形式定义，嵌入 CI/CD 流水线中自动执行。关键词：

  • SAST（静态应用安全测试）：在编码阶段扫描源代码中的安全漏洞。
  • DAST（动态应用安全测试）：在运行时对应用进行黑盒安全扫描。
  • IaC 扫描：在 Terraform / CloudFormation 部署前检查配置合规性。

二、责任共担模型 掌握

CSP 负责"云的安全"（Security OF the Cloud），用户负责"云中的安全"（Security IN the Cloud）。
服务模式CSP 责任用户责任
IaaS物理设施、虚拟化层、网络基础操作系统安全、应用安全、数据安全、身份管理、网络配置（安全组、ACL）
PaaS物理设施 + 操作系统 + 中间件/运行时应用代码安全、数据安全、身份管理、API 密钥管理
SaaS物理设施到应用层全部由 CSP 管理数据内容安全、用户访问控制、配置（共享权限等）
⚠ 责任真空陷阱：无论哪种模式，用户永远对自己的数据、身份凭证和访问策略负责。"CSP 提供了加密功能"不等于"数据已经被加密"，用户必须主动启用并正确配置。

三、IaaS / PaaS / SaaS 安全防护措施及策略要求 掌握

3.1 IaaS 安全防护重点

防护领域具体措施
网络安全VPC（虚拟私有云）隔离、安全组（实例级防火墙）、网络 ACL（子网级）、VPN / 专线加密连接
计算安全操作系统加固、主机安全 agent、漏洞管理、端口最小化、镜像安全扫描
存储安全存储桶访问策略（禁止 Public 读写）、服务端加密 SSE、客户端加密 CSE、版本控制+防删除
密钥管理使用 KMS 集中管理密钥，定期轮换，禁止在代码/配置文件中硬编码密钥
日志审计启用 API 操作日志（CloudTrail/ActionTrail）、配置变更日志，接入 SIEM

3.2 PaaS 安全防护重点

防护领域具体措施
平台配置数据库白名单 IP 访问、禁用公网访问、启用 SSL/TLS 强制加密连接
应用安全Web 应用防火墙（WAF）、API 鉴权 + 限流、防止 SQL 注入 / XSS / CSRF
依赖管理对第三方库和容器镜像进行 SCA（软件成分分析），监控已知漏洞 CVE
运行环境定期升级运行时版本、最小化容器镜像（只包含必要组件）

3.3 SaaS 安全防护重点

防护领域具体措施
身份认证强制 SSO + MFA，支持 SAML / OIDC 联合身份
数据隔离确认 CSP 是否提供租户级数据隔离、数据存储地域选择
访问控制角色与权限细分（管理员 / 编辑者 / 只读），数据分享范围受控
合规认证检查 CSP 是否持有 ISO 27001 / SOC 2 / 等保三级 / C5 等合规资质
数据备份确认 CSP 是否提供数据导出/备份能力，防止供应商锁定导致数据不可迁移

五、评估 CSP（云服务提供商）安全性 熟悉

选择 CSP 不能只看价格和性能——安全能力是选型的第一维度。

5.1 评估六大维度

维度评估要点
① 合规与认证ISO 27001 / SOC 2 Type II / 等保三级 / C5 / PCI-DSS — 认证范围是否覆盖所用地域和服务？
② 基础设施安全数据中心物理安全、DDoS 防护能力（清洗带宽）、可用区/地域冗余架构
③ 数据保护是否支持静态/传输加密？KMS 是否支持客户主密钥（CMK）和自带密钥（BYOK）？数据删除后是否彻底销毁？
④ 身份与访问是否支持 MFA / SSO / 联合身份？IAM 权限颗粒度（到 API 级别）？是否有 Access Analyzer？
⑤ 透明性与审计是否提供完整的 API 操作日志？日志保留时间？是否支持与第三方 SIEM 集成？
⑥ 事件响应SLA 中安全事件的响应时间？是否提供安全公告/漏洞通报？重大事件是否主动通知客户？
某企业选型时发现：A 云价格比 B 云低 15%，但 A 云的 IAM 不支持基于标签的访问策略（ABAC），且 KMS 不支持 BYOK。这意味着企业无法将合规要求的"密钥自主管理"落地——最终选择 B 云。

5.2 评估实践清单

  1. 审查合规资质：逐项核对 CSP 的认证报告（SOC 2、等保、ISO 27001），确认有效期限和覆盖面。
  2. 渗透测试：在合同中确认是否允许客户自行或委托第三方进行渗透测试（Penetration Testing）。
  3. 安全基线检查：使用云安全态势管理（CSPM）工具自动扫描账户/项目的安全配置（如 AWS Trusted Advisor、阿里云安全中心）。
  4. 合同审查：重点关注数据处理协议、数据存储地域、数据删除承诺、安全事件通知时效。
  5. 参考案例：同行业、同规模企业的实际使用案例及安全审计结果。
⚠ 关键结论：同一个 CSP 的不同服务可能有不同的安全认证范围。例如某 CSP 的 IaaS 产品通过了等保三级，但其对象存储服务可能只通过等保二级。评估时必须针对具体使用的服务进行验证。
