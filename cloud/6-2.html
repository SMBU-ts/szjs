概念辨析：常见安全防护措施 vs 安全策略

先分清两个常被混用的词

6.2-0 防护措施 与 安全策略 的关系

熟悉
"安全防护措施"是"用什么手段防"（技术/管理的落地动作）；"安全策略"是"按什么规则防"（制度/原则/基线）。策略决定措施，措施落实策略——两者缺一不可。

🔧 安全防护措施（防护手段）

看得见、摸得着的"动作与工具"：

  • 技术措施：防火墙、WAF、加密、防病毒、入侵检测、漏洞扫描、访问控制列表。
  • 管理措施：安全培训、应急预案演练、账号审批、日志审计制度。
  • 特点：可部署、可检测、可量化（如"每周漏扫一次"）。

📜 安全策略（防护规则）

看不见但指导一切的"原则与要求"：

  • 总体策略：最小权限、纵深防御、默认拒绝、零信任。
  • 具体策略："所有对外端口必须审批""密钥不得硬编码""离职 24 小时内回收账号"。
  • 特点：是制度文件，决定"该上哪些措施"。
  • 策略→措施的关系：策略规定"敏感数据必须加密存储"（规则）→ 措施就是"对数据库开启 TDE 透明加密 + 使用 KMS 托管密钥"（动作）。没有策略，措施会"为了做而做"；没有措施，策略只是空话。
📌 考试答题套路：题目问"安全策略"时答原则/制度/基线（如最小权限、责任共担）；问"防护措施"时答具体技术/管理手段（如 WAF、加密、审计）。
一

云计算核心架构安全（纵深防御）

1.1 纵深防御（Defense in Depth）分层架构

6.2.1 核心架构安全 = 七层纵深防御

掌握
云安全不能只靠单点防护，而要从"物理层 → 网络层 → 主机/计算层 → 应用层 → 数据层 → 身份层 → 安全运维层"层层设防；任意一层被突破，仍有其他层兜底。
图 6-2 七层纵深防御：安全运维（最右）横向贯穿所有层，提供持续监测与响应
层级防护重点常见措施（含云原生服务）
物理安全机房、电力、防灾、人员进出门禁、视频监控、冗余供电/制冷、防灾演练（绝大多数为 CSP 责任）
网络安全隔离与访问控制VPC 私有网络、安全组/ACL、微隔离、WAF 应用防火墙、DDoS 高防、VPN/专线
主机/计算系统与运行环境镜像/模板加固、及时打补丁、堡垒机、HIDS 主机入侵检测、容器镜像扫描
应用安全代码与接口安全开发生命周期（SDLC）、API 鉴权与限流、代码/依赖漏洞扫描、RASP
数据安全数据全生命周期静态/传输加密、脱敏、备份与容灾、DLP 数据防泄露、分类分级
身份安全人/程序身份IAM、强制 MFA、最小权限、SSO、临时凭证（STS）
安全运维监测、审计与响应集中日志、SIEM/SOC、态势感知、应急响应预案、定期渗透测试
  • 纵深防御示例：黑客利用 0day 拿下 Web 应用（应用层破）→ 仍受网络微隔离限制拿不到数据库网段 → 即便拖到数据也是密文（数据安全）→ 异常行为被 SIEM 告警（运维层）。多层拦截，单点失守不等于全面沦陷。

1.2 零信任架构与微隔离

6.2.2 云原生时代的两大关键思想

掌握
① 零信任（Zero Trust）："永不信任，持续验证"——不再默认"内网即安全"，每次访问都需认证、授权、加密。② 微隔离（Micro-segmentation）：把大网络切成细粒度安全域，东西向流量也受控，限制攻击横向移动。

🔐 零信任三大原则

  • 身份即边界：用身份代替 IP/网段作为信任根。
  • 持续验证：每次请求都重新评估风险（设备、位置、行为）。
  • 最小权限 + 默认拒绝：只放行明确授权的访问。

🧱 微隔离的价值

  • 把 Web 区、App 区、DB 区彻底隔开，即使 Web 被控也无法"平推"到数据库。
  • 常用手段：安全组、K8s NetworkPolicy、服务网格 mTLS。
  • 直接支撑"纵深防御"的横向拦截。
⚠ 考试易错点：传统安全以"边界防火墙"为核心、默认内网可信；云安全边界模糊、资源弹性，因此更强调"身份即边界"和"零信任"，不能再假设"进了内网就安全"。

责任共担模型（Shared Responsibility）

2.1 安全责任如何划分

6.2.3 云安全责任分割规则

掌握
CSP 负责"云本身的安全"（Hypervisor、网络、物理、底层硬件）；客户负责"云中的安全"（操作系统、应用、数据、身份与访问配置）。服务模型越往上（IaaS→PaaS→SaaS），CSP 承担越多，客户责任越少。
图 6-3 责任共担模型：越往上（SaaS）CSP 责任占比越大，客户剩余责任越少
服务模型CSP 负责客户负责
IaaS物理、网络基础设施、Hypervisor/虚拟化、部分网络控制Guest OS、中间件、应用、数据、身份、安全组配置、补丁
PaaS在 IaaS 基础上 + 运行时、数据库引擎、OS应用代码、数据内容、访问密钥、配置、部分身份
SaaS几乎全部（应用、运行时、OS、网络、物理）账号与权限、使用配置、终端安全、数据分类、DLP 策略

2.2 "责任真空"陷阱

6.2.4 最容易被忽视的安全盲区

掌握
双方都以为对方负责 → 出现"责任真空"（无人防护的灰色地带）。最典型：数据加密与密钥管理、身份与访问配置、客户端安全基线——无论哪种模型都始终属于客户责任。
⚠ 考试必记：无论 IaaS/PaaS/SaaS，以下永远属于客户责任：
  • 数据加密与密钥管理（CSP 不会替你设密码/密钥策略）；
  • 身份、认证与访问配置（账号、权限、MFA 由客户自己管）；
  • 客户端配置与合规落地（如安全组是否开 0.0.0.0/0、是否启用审计）。
  • 责任真空示例：某公司将云数据库 3306 端口对 0.0.0.0/0 开放且无密码 → 被勒索拖库。这属于"客户侧网络配置责任"，CSP 不背锅；但客户又误以为"上云就有 CSP 兜底"，于是放任不管 → 事故。
三

IaaS / PaaS / SaaS 安全防护措施与策略要求

3.1 IaaS（基础设施即服务）安全防护

6.2.5 IaaS：防护重心在"系统层"

掌握
IaaS 把"裸"的计算/存储/网络给你，客户几乎要自己管 Guest OS 及以上所有东西。防护重点：主机加固、补丁、网络安全组、堡垒机、磁盘加密、操作审计。
防护维度措施与策略要求
网络安全用 VPC 隔离；安全组遵循最小化（默认拒绝，只开必要端口）；禁止 0.0.0.0/0 全开；用 WAF/DDoS 高防保护公网入口
主机加固使用加固镜像/模板；及时打系统补丁（开启自动更新或定期巡检）；关闭无用服务与端口；部署 HIDS 主机入侵检测
访问控制通过堡垒机统一运维入口；SSH 禁止密码登录改密钥；禁用 root 直接远程；操作全程审计录像
数据安全云盘/数据库开启静态加密（TDE/KMS）；定期快照与异地备份；敏感配置文件加密存储
账号与密钥AccessKey 最小权限、定期轮转、不写入代码；使用 STS 临时凭证；开启操作日志（CloudTrail/操作审计）
  • IaaS 场景：自己用云服务器搭网站——你得自己装防火墙、打系统补丁、配安全组、管数据库密码、做磁盘加密。相当于"租了带水电的毛坯房，装修安防全自己来"。
📌 IaaS 策略基线口诀：网不过宽、机必加固、补及时打、盘必加密、管走堡垒、钥要轮转。

3.2 PaaS（平台即服务）安全防护

6.2.6 PaaS：防护重心在"应用与配置"

掌握
PaaS 帮你管好了 OS 和运行时，你只管"应用代码 + 数据 + 配置"。防护重点：安全开发生命周期、依赖/组件漏洞扫描、密钥管理、API 安全、配置基线。
防护维度措施与策略要求
应用安全(SDLC)把安全嵌入开发全流程：需求安全评审、代码审计、依赖/组件漏洞扫描（防 Log4j 类供应链漏洞）、上线前安全测试
密钥管理密钥/证书统一进 KMS/密钥库，严禁硬编码进代码与镜像；使用环境变量或密钥服务动态注入；支持 BYOK 自管密钥
API 安全所有 API 必须鉴权（OAuth2/签名）；限流防刷；输入校验防注入；敏感接口加审计；网关统一管控
配置基线默认安全配置（关闭公开访问、最小权限）；CI/CD 设安全门禁（扫描不过不让发布）；环境隔离（dev/test/prod）
运行时函数计算/容器启用最小权限运行身份；限制出站连接；监控异常调用
  • PaaS 场景：用云数据库 + 函数计算写业务——底层系统由厂商管，你只需管好访问密钥、SQL 权限、代码里的依赖库版本。相当于"租了精装房带物业，你只管布置软装与门锁密码"。
⚠ 易错点：PaaS 看似"省心"，但应用层漏洞（注入、越权、依赖漏洞）和密钥泄露仍由客户负责。把 AK 写进前端代码、用含漏洞的旧版组件，是 PaaS 最常见翻车点。

3.3 SaaS（软件即服务）安全防护

6.2.7 SaaS：防护重心在"账号与使用"

掌握
SaaS 几乎全由厂商运维，客户最该管的是"人、账号、权限、外发内容"。防护重点：SSO、强制 MFA、最小权限、DLP 数据防泄露、租户隔离、登录与操作审计。
防护维度措施与策略要求
身份与认证对接企业 SSO（统一身份）；强制 MFA（防账号被盗）；禁用共享账号；弱密码策略
权限管理最小权限 + RBAC；按角色授权；账号生命周期管理（入职开通、调岗变更、离职 24h 内回收）
数据防泄露配置 DLP 策略限制文件外发/下载/打印；敏感操作二次审批；水印溯源
租户隔离确认厂商多租户逻辑隔离充分（跨租户越权是 SaaS 头号风险）；关注厂商隔离架构说明
审计与合规开启登录与操作审计日志；定期访问复查；用 CASB（云访问安全代理）统一管控多 SaaS
  • SaaS 场景：用在线办公/邮箱/CRM——你重点管好员工账号（开 MFA）、按岗授权、限制文件外发。相当于"用别人运营好的酒店，你只管房卡发给谁、能进哪间房"。
📌 SaaS 客户三件事：① 账号谁能用（SSO+MFA）；② 能看/能下什么（最小权限+DLP）；③ 出事能追谁（审计+CASB）。

四

不同云计算应用的安全策略与部署重点

6.2.9 没有"放之四海皆准"的策略

熟悉
应按应用特征——是否对外暴露、是否含敏感数据、是否强合规、是否海量设备——来确定"部署在哪、重点防什么"。

4.1 对外 Web / 电商

部署重点：扛流量、防暴露面

  • 策略：WAF + DDoS 高防 + 全站 HTTPS + 防爬防刷 + 应用层限流 + 异地多活。
  • 部署：入口挂 CDN/高防；Web 与 DB 分属不同安全域（微隔离）；敏感交易走多因子校验。
  • 合规：支付涉及 PCI DSS；用户隐私遵循个人信息保护法。

4.2 数据密集型 / 大数据

部署重点：加密、备份、分级

  • 策略：静态加密 + 备份容灾 + 脱敏 + 访问分级 + 跨区域复制。
  • 部署：数据仓库/湖开启加密与审计；计算结果脱敏后对外；冷热数据分层存储降低成本。
  • 重点：防止"大数据平台被当成提数后门"——严格字段级权限。

4.3 金融 / 政务（强合规）

部署重点：合规与主权优先

  • 策略：等保三级/四级 + 专属/私有云或金融/政务专区 + 密钥自管（BYOK）+ 全量审计。
  • 部署：优先选符合监管的行业云专区；数据本地化不出境；密钥掌握在客户侧 HSM。
  • 重点：满足监管审计与数据主权，可审计、可追溯、可证明。

4.4 IoT / 边缘计算

部署重点：设备身份与固件可信

  • 策略：设备身份认证 + 设备证书 + 网关加密 + 固件签名校验 + 异常设备隔离。
  • 部署：每台设备发唯一证书；边缘网关做安全接入；海量设备用物联网平台统一管控。
  • 重点：设备数量大、防护弱，易被当成"肉鸡"——设备身份是核心。

4.5 DevOps / 研发上云

部署重点：流水线安全门禁

  • 策略：CI/CD 安全门禁 + 密钥不进代码库 + 镜像扫描 + 最小权限流水线。
  • 部署：代码扫描、依赖扫描、镜像扫描串联进流水线；密钥由 Vault/KMS 注入；制品库签名。
  • 重点："左移"——安全问题在开发阶段就挡住，而非上线后救火。

4.6 混合云 / 多云

部署重点：一致策略与统一身份

  • 策略：统一身份（联邦 SSO）+ 一致安全策略 + 跨云集中审计 + 数据同步加密。
  • 部署：用统一 CSPM（云安全态势管理）看多朵云风险；避免"云间策略不一致留缺口"。
  • 重点：多云最怕"东边墙厚西边墙薄"——策略要拉平。

如何评估 CSP（云服务提供商）安全性

5.1 评估的六大维度

6.2.10 看"证书+透明度+主权+SLA+加密可控+事件响应"

掌握
优先选择有第三方审计背书、合规齐全、透明度高的厂商：从"合规认证、安全透明度、数据主权、SLA 与持久性、加密与密钥控制、事件响应"六个方面系统评估。
维度看什么 / 怎么判断
① 合规认证ISO 27001、SOC 2 Type II、PCI DSS、国内等保三级/四级、CSA STAR——这些是"第三方替你审过"的依据
② 安全透明度是否公开安全白皮书、合规报告（SOC 2 报告）、是否接受渗透测试与漏洞披露（有漏洞赏金计划更佳）
③ 数据位置与主权数据中心地域是否可选、是否满足数据不出境/本地化要求、跨境传输是否有合规机制
④ SLA 与持久性可用性 SLA（如 99.95%）、数据持久性（如 11 个 9 = 99.999999999%）、故障赔付条款是否明确
⑤ 加密与密钥控制是否支持客户自管密钥（BYOK / HYOK）、是否提供 KMS/HSM、是否默认传输加密
⑥ 事件响应是否有明确安全事件通知时效（如 24h 内告知）、应急与溯源能力、事后复盘报告

5.2 评估流程与检查清单

6.2.11 一套可落地的评估步骤

熟悉
评估不是"看广告"，而是"看证据"：先卡合规门槛 → 核透明度 → 验数据主权 → 比 SLA 与赔付 → 测加密可控 → 查事件响应 → 做 PoC 验证。
  1. 明确需求与合规门槛：先定行业（金融/政务要等保+专区）、数据敏感度、是否出境。
  2. 查合规证书：索要 ISO 27001 / SOC 2 / 等保测评报告原件，核对适用范围。
  3. 核透明度：要安全白皮书、SOC 2 报告（可签 NDA 后看）、漏洞披露政策。
  4. 验数据主权：确认地域可选、跨境机制、是否支持本地化部署。
  5. 比 SLA 与赔付：可用性/持久性指标 + 违约赔付是否真有约束力。
  6. 测加密可控：是否 BYOK/HSM、默认加密、密钥轮换机制。
  7. 查事件响应：通知时效、应急流程、历史事故公开度。
  8. PoC 验证：实际测安全组、审计、MFA、密钥注入等能力是否如描述。
  • 金融客户选型：先卡"是否具备等保三级 + 金融云专区 + 支持 BYOK"，再比 SLA 与事故赔付，最后看透明度报告——门槛不过直接淘汰。

5.3 第三方报告怎么读

6.2.12 别被"有认证"三个字糊弄

熟悉
  • ISO 27001：看"认证范围"是否覆盖你用的服务（很多只认证了某几个区域/产品）。
  • SOC 2 Type II：比 Type I 更有说服力（Type II 是"一段时期的持续合规"证据，Type I 只是"某一时点的状态"）。
  • CSA STAR：云安全联盟的成熟度认证，可结合 CAIQ 问卷看控制项覆盖。
  • 国内等保：看测评机构资质 + 备案级别（三级及以上为重要系统）。
📌 读报告要点：盯住"适用范围（Scope）"和"有效期"，认证过期或范围不含你的业务 = 等于没有。

5.4 评估常见陷阱

6.2.13 别踩这些坑

掌握
⚠ 考试/实战易错：
  • 只看"有认证"不看适用范围与有效期；
  • 把"可用性 SLA 高"误当"安全能力强"——SLA 管的是"能不能用"，不是"安不安全"；
  • 忽略数据主权：境外 CSP 可能不满足数据出境合规；
  • 假设 CSP "全包安全"——忘了责任共担里客户自留的那部分；
  • 不问事件通知时效，出事才发现厂商 7 天都不告诉你。
六

考试速记与易错点汇总

6.2-总结 一条主线串起来

速记
策略定规则 → 架构做纵深 → 责任划清边界 → 按服务模型落地防护 → 按应用特征定重点 → 用六维评估选 CSP。
主题一句话考点
防护措施 vs 策略措施=手段（WAF/加密）；策略=规则（最小权限/默认拒绝）
核心架构安全七层纵深防御 + 零信任（身份即边界）+ 微隔离（限横向移动）
责任共担CSP 管"云本身"，客户管"云中"；越往上 CSP 管越多；数据/身份/配置永远客户管
IaaS重系统层：加固、补丁、安全组、堡垒机、磁盘加密、审计
PaaS重应用配置：SDLC、依赖扫描、密钥管理、API 安全、CI/CD 门禁
SaaS重账号使用：SSO、MFA、最小权限、DLP、租户隔离、CASB
应用策略按对外/敏感/合规/设备/研发/多云特征定部署重点
评估 CSP六维：合规、透明度、主权、SLA、加密可控、事件响应；看范围与有效期
⚠ 高频易错（务必记牢）：
  • 云安全 ≠ "买云就自动安全"；安全是 CSP 与客户共同责任。
  • 无论哪种模型，数据加密、身份管理、客户端配置始终归客户。
  • SLA 高 ≠ 安全强；认证要看适用范围与有效期。
  • IaaS 客户责任最大，SaaS 客户责任最小（主要管人）。
