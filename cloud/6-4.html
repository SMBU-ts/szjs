6.4 数据加密与密钥管理

第6章 云计算安全 · 数据的"三种状态"加密必要性 | 对称加密 / 非对称加密 / 哈希 | KMS 密钥管理

一、数据在存储、传输和使用过程中应用加密技术的必要性 掌握

数据在云环境中存在"三种状态"，每种状态都有泄露风险，必须分别施加加密保护。

1.1 数据的三种状态与加密对照

数据状态含义风险对应的加密技术
静态数据
Data at Rest		存储在磁盘、数据库、对象存储、备份快照中的数据物理磁盘被盗、存储桶公开暴露、数据库快照泄露、内部人员恶意拷贝全盘加密（LUKS/BitLocker）、文件级加密、数据库透明加密（TDE）、服务端加密（SSE-S3 / SSE-KMS）、客户端加密（CSE）
传输中数据
Data in Transit		通过网络在客户端与服务器、服务与服务之间传输的数据中间人攻击（MITM）、网络嗅探、DNS 劫持TLS 1.3 / HTTPS（单向或双向认证）、IPsec VPN、SSH
使用中数据
Data in Use		正在被 CPU 处理、存放在内存中的数据内存转储攻击、侧信道攻击、恶意进程读取机密计算（Confidential Computing）、可信执行环境（TEE）、Intel SGX / AMD SEV
⚠ 关键认知：很多数据泄露事件发生的原因是"静态加密已开启，但访问控制配置错误"。加密只能防止物理层面的数据窃取（如硬盘被盗），但不能防止逻辑层面的越权访问（如存储桶公开）。加密必须与 IAM（6.3）配合使用。

1.2 加密的四大必要性

  1. 合规强制要求：《数据安全法》第 27 条、《个人信息保护法》第 51 条、等保 2.0 三级要求对重要数据和个人信息进行加密存储和传输。PCI-DSS（支付卡行业标准）要求持卡人数据必须加密。
  2. 数据泄露的最后一道防线：即使攻击者突破了网络、应用、IAM 所有防线拿到了原始存储文件，如果数据已被强加密且密钥安全存管，数据仍然不可读。
  3. 数据主权与跨境传输：数据在跨国传输时，加密可以满足数据本地化和出境的合规要求。
  4. 用户信任：用户将敏感数据托付到云平台，"端到端加密"是建立信任的核心手段。
某金融科技公司在 AWS 上处理用户交易数据：S3 存储桶同时启用了 SSE-KMS（服务端加密）和客户端加密（CSE），即使 AWS 内部员工也无法读取数据。配合 VPC 端点限制公网访问，5 年来未发生一起数据泄露事件。

二、常见加密方法 掌握

2.1 对称加密（Symmetric Encryption）

加密和解密使用同一个密钥。速度快，适合大数据量加密，但密钥分发和管理困难。
算法密钥长度特点典型应用
AES128 / 192 / 256 bit全球标准、GPU/CPU 硬件加速数据库加密、磁盘加密、SSL/TLS 中的对称加密部分
DES / 3DES56 / 168 bit已过时、不安全，仅兼容老旧系统不应在新系统中使用
SM4（国密）128 bit中国国家密码标准，信创和政务系统强制政务云、金融信创系统中的对称加密
ChaCha20256 bit在无 AES 硬件加速的移动设备上性能更好TLS 1.3 支持的加密套件之一

2.2 非对称加密（Asymmetric Encryption）

使用一对公私钥：公钥加密、私钥解密（或私钥签名、公钥验签）。解决了密钥分发的难题，但计算量远大于对称加密。
算法密钥长度特点典型应用
RSA2048 / 3072 / 4096 bit最广泛应用的非对称算法，加密和签名均可数字证书（X.509）、SSL/TLS 中的密钥交换
ECC（椭圆曲线）256 bit（等效 RSA 3072 bit）相同安全强度下密钥更短、计算更快、功耗更低移动设备、IoT 设备、TLS 1.3 的 ECDHE 密钥交换
SM2（国密）256 bit中国国家密码标准的 ECC 变种，信创强制政务、金融信创中的数字签名和加密
实际应用中，对称与非对称通常是配合使用的：用非对称加密（如 RSA/ECDHE）安全地协商出一个临时对称密钥，然后用对称加密（如 AES-GCM）高效地加密大量数据。这就是 SSL/TLS 的核心设计思想——"用非对称保护密钥，用对称保护数据"。

2.3 哈希算法（Hash）

哈希不是加密（不可逆），但它是数据完整性验证和密码存储的关键技术：

算法输出长度特点/用途
SHA-256256 bit文件完整性校验、区块链、数字签名中的摘要算法
SHA-3可变下一代哈希标准，抗量子计算攻击
bcrypt / Argon2可变专门用于密码存储的哈希，内置加盐和迭代，对抗彩虹表攻击
SM3（国密）256 bit中国国家密码标准的哈希算法
⚠ 常见错误：不要用常规哈希（SHA-256/MD5）直接存储密码——攻击者可以使用彩虹表快速反查。必须使用加盐（Salt）+ 多轮迭代的专用密码哈希（bcrypt / Argon2）。

三、云中的密钥管理（KMS）掌握

KMS（Key Management Service）是云中的密钥保险柜——集中生成、存储、轮换、审计加密密钥，避免密钥分散和硬编码。

3.1 密钥管理的关键概念

概念说明
CMK（客户主密钥）KMS 中的顶级密钥，用于加密数据密钥（DEK）。CMK 本身永不出 KMS。
DEK（数据加密密钥）实际用来加密数据的密钥。由 CMK 加密后存储，使用时从 KMS 解密获取明文。
信封加密CMK 加密 DEK，DEK 加密数据。好处：数据量大时只需调用 KMS 一次解密 DEK，然后用 DEK 在本地高效加解密。
BYOK（自带密钥）用户将自己的密钥导入 KMS，满足"密钥不出自己控制范围"的合规要求。
自动轮换KMS 按策略（如每年）自动生成新版本 CMK，旧版本保留用于解密历史数据。
HSM（硬件安全模块）专用的硬件加密设备，密钥存储在防篡改的物理芯片中。KMS 通常底层由 HSM 支持。

3.2 密钥管理最佳实践

  1. CMK 永不出 HSM：主密钥的明文只在硬件安全模块内存中短暂存在，绝不暴露在外。
  2. 信封加密：用 CMK 加密 DEK，DEK 加密数据——解决"大数据加密性能"与"密钥安全存储"的矛盾。
  3. 密钥轮换：定期自动轮换密钥（建议至少每年一次），降低密钥泄露的影响范围。
  4. 最小权限访问 KMS：仅授权特定的 IAM 角色才能使用 KMS 密钥，且把"加密"和"解密"权限分开授予。
  5. 审计所有密钥操作：KMS 的每一次加密/解密/轮换/删除都应记录到不可篡改的日志中（如 AWS CloudTrail）。
  6. 密钥分层：不同环境（开发/测试/生产）、不同应用、不同数据分类级别的数据使用不同的 CMK，缩小单密钥泄露的爆炸半径。

3.3 各云厂商 KMS 对比

云厂商KMS 产品名核心能力
AWSAWS KMS + CloudHSM与 S3/EBS/RDS 深度集成，支持自动轮换、BYOK、信封加密；CloudHSM 提供专用物理 HSM
阿里云KMS + 加密服务（HSM）支持国密 SM2/SM4、BYOK、信封加密、与 OSS/RDS 集成
华为云KMS（数据加密服务 DEW）一站式密钥管理、支持 SM 系列国密、密钥对管理
腾讯云KMS（密钥管理系统）BYOK、信封加密、白盒密钥（移动端）、与 COS/CBS 集成

3.4 数据加密的全生命周期小结

数据加密不是"开启一个开关"就完事了，而是贯穿数据创建→存储→传输→使用→备份→归档→销毁的全流程：

  • 创建：应用层客户端加密（CSE）
  • 存储：服务端加密（SSE）+ 数据库透明加密（TDE）
  • 传输：TLS 1.3 强制 + 双向 mTLS（微服务间）
  • 使用：机密计算（TEE）+ 内存加密
  • 备份：加密快照 + 异地加密存储
  • 归档：长期归档加密（密钥永久保存）
  • 销毁：加密擦除（Crypto-Shredding）——销毁密钥即销毁数据
⚠ 终极提醒：加密的强大程度 = min(算法强度, 密钥管理安全性)。使用 AES-256 但如果密钥写在代码里上传到 GitHub，安全强度 = 0。
